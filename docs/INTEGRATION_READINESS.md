## Local checks and cloud boundaries

Run `npm ci`, `npm test`, `npm run typecheck`, `npm run lint`, and `npm run build` for reproducible local checks. `npm audit --omit=dev` checks shipped dependencies. `npm run verify:production -- .env.staging` performs cloud mutations (temporary Auth user, Firestore document and Storage object) and network checks; the script now refuses to run unless explicitly enabled and the target project ID matches. Do not use production credentials for this verification.

For an authorized staging project only, set `VERIFY_ENVIRONMENT=staging`, `VERIFY_ALLOW_CLOUD_MUTATIONS=true`, and `VERIFY_FIREBASE_PROJECT_ID` to the exact staging project ID in the process environment. The script rejects other environments and mismatched project IDs. Then run:

```powershell
$env:VERIFY_ALLOW_CLOUD_MUTATIONS = "true"
$env:VERIFY_ENVIRONMENT = "staging"
$env:VERIFY_FIREBASE_PROJECT_ID = "your-staging-project-id"
npm run verify:production -- .env.staging
Remove-Item Env:VERIFY_ALLOW_CLOUD_MUTATIONS
Remove-Item Env:VERIFY_ENVIRONMENT
Remove-Item Env:VERIFY_FIREBASE_PROJECT_ID
```

The verification script creates uniquely named disposable test resources and attempts cleanup in `finally` blocks. Review its output and cloud logs; a successful health check is not proof of the complete voice, feedback, resume, PDF, history, or code execution journeys.

## Firebase index and rules deployment

The exact checked-in definitions are `firestore.indexes.json`, `firestore.rules`, and `storage.rules`, referenced by `firebase.json`. An authorized project administrator should first confirm the target project with `firebase projects:list`, then deploy to the explicit project:

```powershell
firebase deploy --only firestore:indexes,firestore:rules,storage --project your-project-id
```

Verify the command's project ID and success output, then inspect the Firebase console's Firestore indexes until each index is enabled. The deployment command is documented for the project owner; it was not run in this phase.

## Health endpoint

`GET /api/health` is a read-free liveness response for hosting probes. `GET /api/health?deep=1` checks Firebase Auth, Firestore, Storage write/delete, AI configuration, and Judge0 reachability. In production, the deep check requires `INTERNAL_API_SECRET` in the `x-prepwise-internal-secret` header because it uses privileged Firebase Admin operations and writes a temporary Storage object. The `verify:production` script sends this header. Do not publish the secret or attach it to an unauthenticated public probe.
